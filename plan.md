# IPT Matching Marketplace — Plan

An independent, two-sided marketplace connecting Tanzanian university students with **organizations** (companies and institutions) for **Industrial Practical Training (IPT)**. Runs autonomously (no university integrations): students register on their own and universities are only an optional affiliation record. Students pay an application fee via Mobile Money before an application is unlocked and submitted to an organization.

> **Terminology (read this first).** The code, URLs and UI now say **Organization**, not Company. Older dated entries in section 12 predate the rename and still say `CompanyProfile` / `company-*` / `/company/`; the mapping is in the "Rename glossary" at the top of section 12. The `apps/companies/` package, the `companies` app label and `Application.company_message` kept their old names on purpose.

## 3. Security & Authorization Protocol

- **Students**: upload scanned Student ID + official Semester Results Matrix → account stays `PENDING_VERIFICATION` until Platform Admin approves.
- **Organizations**: upload BRELA certificate, TIN certificate, Business License → cannot post slots or view applicants until profile is `APPROVED`.
- **Platform roles**: `ADMIN` (capability matrix from `AdminRole`: modules `user_management`, `slot_verification`, `financial_ledger`, `system_metrics` x `view/create/edit/delete`) and `SUPER_ADMIN` (everything; roles/settings/templates pages are super-admin only). Console gate is `core.views._require_admin`.
- **Organization RBAC** (`apps/companies/permissions.py`, enforced by `@org_permission_required(...)` on every organization view, never only in templates): `OWNER` ⊃ `MANAGER` ⊃ `RECRUITER`. Recruiter: view org, view/manage slots, view applicants. Manager adds edit profile, manage documents, accept applicants. Owner adds manage members. `UNIVERSITY_COORDINATOR` / `UNIVERSITY_SUPERVISOR` exist but are read-only placeholders until university workspaces are built. All queries are scoped by `slot__organization=` / `organization=` so one organization can never read another's applicants or documents.
- **Multi-account organizations**: an organization has up to **5 active members** (`OrganizationMember`, `MAX_ORGANIZATION_ACCOUNTS`) and up to **5 concurrent logins** (`OrganizationSession`, `MAX_ORGANIZATION_CONCURRENT_LOGINS`; tracked from `user_logged_in/out` signals in `companies/apps.py`; a 6th login is refused until a session ends or expires). Owners/managers add and remove staff from the organization profile page.
- **Suspension**: platform admins can suspend/reactivate a student or a whole organization (sets `is_active=False` + `suspended_at`); suspended organizations are hidden from search and take no new applications. Every admin action is written to the hash-chained audit log.
- DRF permission classes: `IsStudent / IsOrganization / IsPlatformAdmin / IsPlatformSuperAdmin / IsVerifiedStudent / IsApprovedOrganization / IsOrganizationOwner`.
- Cross-service auth: **no permanent API tokens** (removed 2026-11-09). The browser fetches a single-use, 60 s WebSocket ticket from `/api/auth/ws-ticket/` (Redis key `ipt:wsticket:*`, `apps/core/ws_tickets.py`); FastAPI redeems it with an atomic `GETDEL` (`realtime/app/core/auth.py`). DRF uses `SessionAuthentication` only. The `authtoken_token` table is now unused.
- **Identity & access management (Feature 2)**: OTP registration/recovery, 5-minute login lockout, 10-minute one-device sessions, verified email/phone changes, administrator accounts + MFA (TOTP / FIDO2), M-of-N recovery, break-glass accounts, structured org audit trail, soft member removal. Full detail in the section **"Feature 2 — Identity & Access Management (IAM) — DONE"** below.
- Webhook security: HMAC-SHA256 signature + idempotency by `gateway_txn_id` + replay rejection.
- Upload validation: **< 2 MB** for all documents and images, magic-byte MIME check, extension allowlist, SHA-256 checksum.
- Documents served only through permission-checked views (never bare MEDIA_URL).

## 4. Database Schema (PostgreSQL)

- **accounts_user** — `role` (STUDENT/ORGANIZATION/ADMIN/SUPER_ADMIN), `admin_role` FK (capability matrix), `email` unique (USERNAME_FIELD), `phone`, `email_verified`, `phone_verified`, `suspended_at` + `suspension_reason`, `deletion_requested_at`, `promo_sms_optout`. Organization users have no first/last name (`full_name` falls back to the organization name).
- **accounts_adminrole** — name, permissions (module x capability JSON), is_system.
- **students_university** — name (unique, case-insensitive), abbreviation, institution_type (UNIVERSITY/COLLEGE/INSTITUTE), region FK, website, `verification_status` (APPROVED = selectable by everyone; PENDING = a student's "not listed" suggestion; REJECTED), `suggested_by` FK. Seeded (131) from `data/tanzania_institutions.json` by migration `students.0005` and `manage.py seed_universities`.
- **students_studentprofile** — `university` FK (nullable, optional), `graduation_year`, `student_id` (registration number), course, `academic_year`, `education_level` (TCU 4-10), gpa, skills (JSON), gender, photos, region/district/ward FKs, `reapplication_credit`, `verification_status` (PENDING/APPROVED/REJECTED), rejection_reason.
- **companies_organization** (model `Organization`) — optional one-to-one `user` (the creating owner), name (unique), `organization_type` (COMPANY/UNIVERSITY/INSTITUTION; only COMPANY can be registered today), industry, description, email, phone, address/street, region/district/ward FKs, `verification_status`, rejection_reason, `suspended_at` + `suspension_reason`.
- **companies_organizationmember** — organization FK, user FK, `role` (OWNER/MANAGER/RECRUITER/UNIVERSITY_COORDINATOR/UNIVERSITY_SUPERVISOR), `membership_status` (ACTIVE/INVITED/SUSPENDED), `UNIQUE(organization, user)`, max 5 ACTIVE per organization.
- **companies_organizationsession** — organization FK, user FK, `session_key` (unique); drives the 5-concurrent-logins cap.
- **core_report** — reporter FK, optional organization FK, category (FRAUD/MISLEADING/PAYMENT/ABUSE/OTHER), subject, description, status (OPEN/IN_REVIEW/RESOLVED/DISMISSED), admin_notes, handled_by/handled_at.
- **documents_document** — owner, `doc_type` (STUDENT_ID, RESULTS_MATRIX, CV, INTRO_LETTER, BRELA_CERT, TIN_CERT, BUSINESS_LICENSE), file, mime_type, size, sha256.
- **locations_region / locations_district** — seeded reference data (31 regions, ~184 districts).
- **slots_slot** — `organization` FK (APPROVED, not suspended), title, industry, role_type, district FK, street, department/course, `academic_year`, `education_level`, **`application_deadline` (optional)**, capacity, stipend, skills_required (JSON), status `OPEN | FULL | PAUSED | CLOSED`, derived `available_count`, `deadline_passed`.
- **payments_payment** — reference_id (unique), student FK, application FK, amount (TZS), method (M_PESA/TIGO_PESA/AIRTEL_MONEY), gateway (MOCK/SELCOM/PESAPAL), gateway_txn_id, callback_payload (JSON), status (PENDING/PAID/FAILED), `is_paid`, paid_at, receipt_pdf.
- **applications_application** — student FK, slot FK, payment FK (nullable 1:1), status `PENDING → PAID → UNPAID` (payment-status model), `payment_deadline` (created + 3h), `is_accepted` (bool, company acceptance/SMS flag), `UNIQUE(student, slot)`.

### Enforced invariants
1. **Paid visibility** — company-facing queryset filters `status='PAID'`; a PostgreSQL `BEFORE UPDATE` trigger rejects any transition to `PAID` without a verified payment.
2. **Capacity lock** — service layer uses `select_for_update` on the slot; `Slot.booked_count` counts `PENDING + PAID` (a pending application reserves a seat). A trigger rejects inserts/updates that exceed `capacity` (counts PENDING + PAID).
3. **Unpaid expiry** — Celery beat `applications.expire_unpaid` (every 10 min) marks PENDING applications past `payment_deadline` as `UNPAID`, fails their pending payments, and releases the seat; the student can re-book to restart.

## 5. Business Flow (revised — no interview/decline)

1. **Apply Now** → lock slot → reject if full → create `Application` `PENDING` (invisible to company; reserves a seat) with a 3-hour `payment_deadline`.
2. Payment overlay (mock M-Pesa/Tigo/Airtel) → gateway callback → FastAPI validates HMAC + idempotency → `Payment PAID` → application `PAID` → Celery: receipt email, submitted SMS, notification fan-out, slot capacity recompute. Company acceptance (optional) sets `is_accepted`.
3. Company sees **all PAID applicants** on the slot (in-browser doc viewer) and can send the **acceptance SMS**.
4. Slot shows `FULL` when capacity reached (pending + paid); further applies blocked. Unpaid pending applications expire after 3h → `UNPAID` → seat released.

## 6. Two Notification Types

- **Type A — Application**: (1) **Email** receipt (PDF, reference ID, amount, company, slot); (2) **SMS** "application sent" with Application ID, Company Name, Slot selected.
- **Type B — Acceptance**: company-triggered **SMS** → "check your email for the acceptance letter / further instructions".

## 7. Student Filters (live reduction)

Marketplace fetches `/api/slots/search/?region=&district=&department=&academic_year=&education_level=&organization=` on every filter change (cascading region→district loads from the locations API; `department` is the academic-discipline search and `organization` is a name search). Results are cached in Redis under a versioned key that includes every parameter. Each card shows capacity, stipend and the application deadline; once the deadline passes it reads "Applications closed" and applying is refused server-side.

## 9. FastAPI Async Layer

- `GET /ws/notifications/{user_id}?ticket=` — persistent WebSocket (`user_id` is a UUID string); authenticated with a single-use ticket; the Redis pub/sub subscriber pushes notifications and `session_revoked` events (the socket is then closed with 4401).
- `POST /api/v1/payments/callback` — async: HMAC validate + idempotency → update DB → enqueue Celery tasks.
- `POST /api/v1/payments/mock/initiate` + `/mock/callback` — mock gateway simulator (dev-only).

### Feature 2 — Identity & Access Management (IAM) — DONE (2026-11-09)

Built in order (tests: `pytest apps`, 100+ tests; new files `accounts/tests.py`, `accounts/test_contact_and_password.py`, `accounts/test_admin_mfa.py`, `companies/test_iam_org.py`). Migrations: `accounts.0007–0010`, `companies.0005`, `core.0005` (run `python manage.py migrate`; 0007 adds a unique-phone constraint, so duplicate phone numbers must be resolved first).

**Step 1 — closed authentication holes**
- Removed `TokenAuthentication`, `/api/auth/token/`, `/api/auth/my-token/` (permanent, never revoked, bypassed session rules). WebSocket uses single-use tickets (see section 3).
- Passwords no longer travel through Celery; login is inline; registration task takes `password_hash`.
- `/auth/finalize/`: `TimestampSigner` (salt `accounts.finalize-auth`, 60 s), stored in the session that started the task, consumed on use. `/auth/task-status/<id>/` only answers the session that created the task.
- Old "reset password by knowing email + phone" flow removed (it was an account takeover); recovery needs an OTP. Realtime WS path typed `user_id` as `int` although ids are UUIDs: fixed (not tested live).

**Step 2 — OTP, lockout, unique phone** (`accounts/otp.py`, `core/lockout.py`)
- `OneTimeCode` rows: 6 digits, **5 min** expiry, single use, **HMAC-hashed** (never stored plain), 5 guesses then dead, a new code invalidates the previous one, resend limited by the existing token bucket (`consume`, burst 3 then 1/min). Delivered **synchronously** (a Celery task would put the code on the broker).
- **Registration**: account is created first, then an **email-only** OTP (no channel choice) is required before the first sign-in (students and organization members; admins are exempt). **Recovery and later flows offer email or SMS**; a code is only sent to a method already verified on the account; identical response whether or not the account exists. Recovery is three screens: email → choose method (`/auth/reset-password/method/`) → code → new password. A password change signs out all other sessions (Django ties sessions to the password hash).
- **Lockout** (changed 2026-11-16, see "Security hardening after the Playwright review"): 5 failed logins from one address on an email (`LOGIN_LOCKOUT_ATTEMPTS`) lock that address out for that email for 5 min (`LOGIN_LOCKOUT_SECONDS`); a separate account-wide lock needs `LOGIN_LOCKOUT_ACCOUNT_ATTEMPTS` (25) failures from all addresses. Both key on the submitted email whether or not an account exists; never disables the account; cleared on success. Works alongside the existing token-bucket limiter (not a second limiter). Originally the lock was keyed on the email alone, so anyone could lock out a known email for 5 minutes; that is no longer possible from a single address.
- **Phones** are stored digits-only and unique (DB partial unique index `uniq_user_phone_nonblank`); emails already unique.

**Step 3 — sessions** (`accounts/sessions.py`, `SessionPolicyMiddleware`)
- **10 min idle** lifetime (`SESSION_COOKIE_AGE=600`), enforced on the server per request (`login_at` / `active_at` in the session) and by the session row expiry, so it holds offline. Real activity restarts it: `session-guard.js` reports mouse/keyboard/touch/scroll to `POST /auth/session-extend/` (at most every 10 s; `sessions.touch`), while `/auth/session-status/` polling never extends. A hard ceiling from login, `SESSION_ABSOLUTE_MAX_SECONDS` (default 3 h), still ends the session however active the user is. HttpOnly, SameSite=Lax, Secure in prod; nothing in localStorage/sessionStorage. Session ids are Django CSPRNG (>=160 bits), rotated at login, MFA elevation, hardware step-up, forced password change.
- **One live session per account**: `User.current_session_key`; a new login destroys the old session row and publishes `session_revoked` on `ipt:notify` (ws.js redirects the old tabs; the realtime service closes the socket). `static/js/session-guard.js` polls `/auth/session-status/` every 20 s and warns 60 s before expiry. The backend alone decides validity.
- The organization cap now counts **people** (max 5 members => 5 logins); a member signing in again replaces their own session. Logout destroys the server session; authenticated responses send `Cache-Control: no-store`.
- Role changes / removal / suspension call `revoke_user_session` so the user must sign in again with a new id. The client-side idle logout in `base.html` now matches the server (10 minutes, popup with a 30 s countdown; `session-guard.js` only warns at 30 s for the 3 h ceiling).

## Login speed (3+ s -> well under 1 s)

## Slot posting and applying upgrade (fixes + features A–J)

Decisions made with the owner in a question round before building.

**Fixes**
- **Paused / closed slots really stop applications.** Search excludes `PAUSED` and `CLOSED`; `create_application` refuses them (unless the student already holds a seat). `Slot.refresh_status` never changes a `PAUSED`/`CLOSED` slot, and resuming a paused slot that filled up sets it to `FULL`, not `OPEN`.
- **Eligibility** (`applications.services.eligibility_blocker`): the slot's education level is a *minimum* (a higher level may apply); the academic year is only checked when the student is at the slot's level (Higher Diploma) or has no level. Unknown values on the profile are never held against the student. Enforced in `create_application`, in the `apply` view (GET and POST) and shown on marketplace cards ("Requires Level X", mirrored in `marketplace.js`).
- **Credit re-application** now creates the Payment and goes through `finalize_verified_payment` (gateway id `CREDIT-REAPPLICATION`), inside one transaction. Before, it set the application to PAID before any Payment existed, which the "PAID needs a verified payment" trigger refuses (found by reading; the new test covers the working path). The Payment keeps the full fee amount (owner's choice).
- **Slot industry** was never set (not on the form). `SlotForm` has an optional `industry` field, the views default it to the organization's industry, and `slots.0005_backfill_industry` fills old blank slots.

## Realtime: WebSocket refused with 403, Redis pool exhausted (fixed 2026-11-16)
- **Symptom:** the browser console repeats `WebSocket connection to 'ws://127.0.0.1:8001/ws/notifications/...' failed` while Django, FastAPI and Redis are all up. The realtime service answers the handshake with HTTP 403 and the ticket stays in Redis (never redeemed); `PUBSUB NUMSUB ipt:notify` shows 0 subscribers, so no pushes are delivered either. Only a restart of the realtime service cleared it.
- **Cause:** `notify_subscriber_task` (`realtime/app/ws/router.py`) created a new `PubSub` on every retry and never closed it. An attempt that failed after it had obtained its connection (for example a non-object payload on `ipt:notify`) kept that connection out of the shared client's pool for good; redis-py caps the pool at 100. With the pool exhausted every `get_pub()` call raised `MaxConnectionsError`, including the `GETDEL` in `validate_ticket`, which swallowed the error and returned False. Seen in a realtime process that had been up for two days: pool 100/100 in use, subscriber stuck in its 1 s retry loop. A refused connect does not leak (a plain 130 s Redis outage recovered), and which error repeated 100 times in that process is not known because its output was not captured; WSL Redis had restarted early in its life.
- **Fix:** the subscriber closes its `PubSub` with `aclose()` in `finally` (returns the connection); non-object payloads on `ipt:notify` are skipped instead of crashing the loop; `validate_ticket` retries the `GETDEL` once on a connection error (after a Redis restart the first command on an idle pooled connection fails); `validate_ticket` and the subscriber loop now log their Redis failures (the subscriber once per outage). The shared client and the payment-webhook lock are unchanged.
- **Verified** against a throwaway Redis with the pool capped at 5 (`REDIS_URL=...?max_connections=5`): before, 7 malformed messages made every handshake fail for good; after, handshakes pass through 7 malformed messages and 6 Redis restarts.
- `static/js/ws.js` gives up after 8 retries, so an open tab needs a reload once the service is back.
- **Organization slot and applicant pages on phones (2026-11-16):** (1) `80% Filled` (a doubled `%%` inside blocktrans); (2) stipend shown as `TZS 300,000 / month` via the `money` filter (`apps/core/templatetags/money_tags.py`); (3) wrap-safe separators `.ipt-meta` / `.ipt-meta-item` instead of hand-written bullets; (4) short labels in the slot Applicants filters (`.ipt-compact-filters`); (5) My Slots actions: Applicants + Edit + a labelled More menu (Delete last); (6/7) titles wrap to two lines, full-width spots-left bar; (8/9) the per-slot Applicants page reuses `_applicant_row.html` (`hide_slot=True` shows year, graduation and applied/paid dates) with a summary line and a collapsed "Slot statistics" above the list (`_slot_overview.html`); (10) every Accept confirms with the student name (bulk: with the count, and refuses an empty selection); (11) All applicants: search on its own row, Filters + Export below, "Apply filters" in the panel; (12) bulk accept is a bottom bar shown once a box is ticked; (13) row checkbox sits in a 44 px label with the avatar; (14-17) the slot form has five sections, the stipend row now really hides (the old script never found it), role type suggestions, plain-text date echo, 48 px Cancel. ## Security hardening after the Playwright review (2026-11-16)

A browser-driven security pass (Chrome via Playwright, dev stack) found no exploitable bug: access control, CSRF, payment signatures, WebSocket tickets, uploads, XSS escaping and sessions all held. These findings were fixed:

- **Content-Security-Policy without `'unsafe-inline'` for scripts.** `settings.SECURE_CSP` (base.py) + Django's built-in `ContentSecurityPolicyMiddleware` + the `django.template.context_processors.csp` context processor. `script-src 'self' 'nonce-<per request>'`; styles keep `'unsafe-inline'` (inline `style=""` is used widely and cannot run code); `object-src 'none'` added. The old hard-coded policy in `SecurityHeadersMiddleware` is gone (one definition only). A view that sets its own policy (the sandboxed document viewer) keeps it.
  - Every inline `<script>` in a template must be `<script nonce="{{ csp_nonce }}">`. Inline `on*=` handlers and `javascript:` links no longer work: use the `data-*` actions handled by `static/js/csp-actions.js` (`data-ipt-confirm`, `data-autosubmit`, `data-toggle-password`, `data-print`, `data-history-back`, `data-stop-click`, `data-no-submit`, `data-href`) or an `addEventListener` in a nonce'd script.
  - The four stylesheet `<link media="print" onload=...>` tags now carry `data-ipt-css`; the head script catches their `load`/`error` in the capture phase (registered before the first link), so the skeleton shell and the `media="all"` swap still work.
  - Translation catalog: the terms-checkbox `{% blocktrans %}` in `register.html` contained `onclick="event.stopPropagation()"`, which is part of its msgid, so the same four lines in `locale/sw/.../django.po` were changed to `data-stop-click` and `scripts/build_translations.py` rebuilt the `.mo`.
  - Guard: `apps/core/test_csp.py` scans every template (admin pages included) for inline handlers, `javascript:` URLs and un-nonced inline scripts, and checks the header, nonce matching and per-response nonce freshness.

## On-screen keyboard behaviour (2026-11-17)

`static/js/keyboard.js` (loaded from `base.html`, the only full-page template) tunes every `<input>`/`<textarea>` on the platform, including ones added later (MutationObserver). It never overrides an attribute a template or form widget already sets.

- `type=email` → `inputmode=email`; `type=tel` or phone-named → `inputmode=tel`; `type=number` → `numeric` (or `decimal` when `step` has a fraction; fields that may be negative are left alone because iOS's numeric pad has no minus); `type=search`/`q` → `inputmode=search` + `enterkeyhint=search`; six-character `code`/`otp` fields → `numeric` + `one-time-code` (longer recovery codes stay alphanumeric).
- Email, password, phone, code and search fields get `autocapitalize=none`, `autocorrect=off`, `spellcheck=false`; name/title/department-style fields get `autocapitalize=words`.
- `enterkeyhint`: GET (filter/search) forms show a Search key and submit on Enter; multi-field POST forms show Next on every field but the last (Go). On touch devices (`pointer: coarse`) Enter on a "Next" field moves focus to the next field instead of submitting early; desktop keeps native Enter-submits.
- On touch devices a focused field is scrolled into view when the keyboard opens (focusin + `visualViewport` resize). `base.html` viewport adds `interactive-widget=resizes-content` so Chrome Android resizes the layout instead of overlaying it.
- Django widgets: first/last name got `autocomplete=given-name/family-name`. Text inputs are already 16 px (`responsive.css`), so iOS does not zoom on focus.
- Guard: `apps/core/test_csp.py::test_every_page_loads_the_keyboard_script_and_a_keyboard_aware_viewport`.

## Fee vouchers and sponsor codes (2026-11-20)

Admin-issued discount codes for the application fee, a signup reference that applies one automatically to a student's first application, and a ledger that separates gross fees, discounts and cash. New app `backend/apps/vouchers/` (in `INSTALLED_APPS`).

**Decisions (asked per feature before building):** admins issue batches (no sponsor self-service or sponsor payment flow yet); discounts are percentage, fixed TZS or a 100% waiver; a use is reserved when the student applies and given back when the application expires, is released or is cancelled; restrictions are optional and every filled one must match; one 100% waiver per student overall; the ledger fix (credit payments no longer count as revenue) was approved; the code is entered on the apply page; registration never fails because of a bad code.

- **Models.** `VoucherBatch` (terms, validity window, per-student limit, budget cap, restrictions), `FeeVoucher` (one code; stored upper case letters+digits only, `normalize_code`; generated codes are `IPT` + 8 characters from an alphabet without 0/O/1/I, shown as `IPT-XXXX-XXXX`; a campaign code may be custom), `VoucherRedemption` (one per application: fee, discount, amount charged, `from_signup`) and `SignupReference` (what a student typed at registration: SAVED or REJECTED + reason).
- **No "used" counter.** A redemption holds a use of its code, a share of the batch budget and a student's per-batch limit only while its application is PENDING or PAID (`ACTIVE_APPLICATION_STATUSES`), exactly like a slot seat. Expiry (`applications.expire_unpaid`), "release seat" and cancellation therefore free the use with no write, and the FastAPI webhook needs no change: it already compares the callback amount with `Payment.amount`, which is the discounted amount. "Discount given" in the ledger counts only PAID applications.
- **Pricing is settled at checkout.** `Payment.amount` is the amount to pay (paid payments are immutable, so it cannot be adjusted later); the gross fee and discount live on the redemption. A 100% voucher creates the Payment at 0 and finalizes it through `finalize_verified_payment` with `gateway_txn_id="VOUCHER-<code>"` (same path as the cancellation credit, `CREDIT-REAPPLICATION`). Prefixes: `payments.utils.CREDIT_TXN_PREFIX` / `VOUCHER_TXN_PREFIX`.
- **Rules live in one place:** `vouchers.services.voucher_blocker(voucher, user=, profile=, slot=)` returns a student-safe message or `""` (same shape as `eligibility_blocker`). With no profile/slot yet (right after registration) only the rules that can be decided are checked. Unknown, revoked and paused codes all say "This code is not valid."
- **Reserving** (`services.reserve`, inside the apply transaction): `select_for_update` on the code, its batch and the student's profile (last use, budget overspend, two waivers by applying twice at once). It replaces the application's existing redemption (a re-booked seat). `resolve_checkout_offer` order: a typed code (errors shown on the form) > the redemption the application already holds (re-checked on re-book; if it no longer works it is dropped, the full fee is charged and the student is told) > the registration offer (a failure only shows a notice) . The cancellation credit wins over any voucher and the voucher is not consumed.
- **Database guarantees** (`vouchers/migrations/0002_redemption_immutable.py`, trigger `ipt_voucher_redemption_guard`): an INSERT beyond the code's `max_uses` (counting PENDING+PAID applications) is refused; a redemption is never UPDATEd; one whose application is PAID cannot be deleted. An unpaid one may be deleted (re-book drops it).
- **Registration reference.** `RegisterForm.voucher_code` (optional, students only, never an error) -> `process_registration_task` -> `attach_signup_reference` (after the user commits, wrapped so it cannot undo signup). Valid -> SAVED + in-app notice "Your offer is saved"; otherwise REJECTED with the reason + notice. Registration time can only check validity, expiry, cap, signup window and named-email list (there is no profile yet); the rest is checked when applying. `/register/?code=...` pre-fills the field. The offer applies automatically on the apply page until it holds a use for the student (per-student limit 1 = "first application"). Pre-fill and the field are hidden for organization sign-ups (`data-student-only`).
- **Abuse limits.** Code check endpoint `student-voucher-check` (`POST /student/voucher/check/`): token bucket 8 burst, 1 per 20 s, fail-closed, generic wording; the apply POST keeps its own bucket (3 per minute); registration keeps its own per-IP/per-email buckets and the notice after signup is the only feedback.
- **Admin console** (`/platform/vouchers/`, `.../new/`, `.../<id>/`; `views_admin.py`): reuses the `financial_ledger` module (view to see; edit to issue, pause, revoke, add codes or export). Issuing and the POST actions use `@hardware_reverify`; every action goes through `audit_event` (module "Vouchers"); exporting the codes CSV is audited and needs the edit capability because a code is a bearer secret. Pages are English (admin console).
- **Ledger** (`/platform/ledger/`): header shows gross fees, voucher discounts, re-application credits and cash collected (`vouchers.stats.ledger_totals`; cached 30 s under `admin:ledger-totals-v2`); the table has Source / Fee / Discount / Paid columns, a `source` filter (cash, voucher, credit) and finds rows by voucher code. **Revenue is now cash only:** payments whose `gateway_txn_id` starts with `CREDIT-` are excluded from the ledger total, the metrics page `total_fees`, the revenue chart and the `ledger.aggregate` snapshot (they used to count the full fee for a free re-application, so existing totals go down).
- **Receipts and student pages:** receipt PDF lists the fee, the voucher discount and the amount paid; the payment page shows the breakdown; the receipt email says so when a voucher covered everything. The apply page shows the offer, a "Check" button (priced preview, nothing reserved) and the final price.
- **Kiswahili:** student-facing strings are in `scripts/sw/ui.json`; the admin pages/modules are listed in `apps/core/test_translations.py` as English-only.
- **Not built (on purpose):** sponsor-purchased batches (a second payment flow, invoices, refunds on unused codes), sponsor self-service issuing, a "first application only" batch restriction, year-of-study/gender restrictions. Add a restriction by adding a field on `VoucherBatch`, a check in `student_restriction_blocker` / `slot_restriction_blocker` and a field in `vouchers/forms.py`.
- **Tests:** `apps/vouchers/tests.py` (pricing, every restriction, caps and release, apply flow, registration reference, triggers, admin console permissions, ledger split).
